## 1. 技术目标与约束

- **平台**：Windows 10/11 桌面应用
- **语言**：Python 3.12
- **形态**：本地单机应用，数据存本地 SQLite，预留云端同步扩展点
- **UI 风格**：现代简洁（Fluent Design），浅色主题优先

## 2. 技术选型

| 类别 | 选型 | 说明与理由 |
| --- | --- | --- |
| 语言运行时 | Python 3.12 | 生态成熟，开发效率高 |
| GUI 框架 | **PySide6**（Qt 6.7+） | Qt 官方 Python 绑定；LGPL 协议对闭源/商用友好（动态链接即可）；Widgets 成熟稳定，适合桌面工具 |
| UI 组件库 | **PySide6-Fluent-Widgets**（qfluentwidgets） | 基于 PySide6 的 Fluent Design 组件库，开箱即用的现代简洁 UI（导航、卡片、对话框、InfoBar 提示、深浅主题） |
| ORM / 数据库 | **SQLAlchemy 2.x + SQLite** | SQLite 零依赖内嵌存储；SQLAlchemy 便于后续迁移到云端数据库 |
| 数据库迁移 | Alembic | 表结构版本化管理 |
| 图表 | PySide6.QtCharts（柱状/折线/扇形）+ 自绘 QWidget（热力图） | QtCharts 随 PySide6 自带，无额外依赖；热力图用 QPainter 自绘，灵活可控 |
| 打包分发 | PyInstaller（单目录模式） | 成熟稳定；Nuitka 作为备选（启动更快、反编译保护更好） |
| 测试 | pytest + pytest-qt | 服务层单元测试 + 关键 UI 流程测试 |
| 代码质量 | ruff（lint + format） | 单一工具搞定，速度快 |

### 2.1 关于 qfluentwidgets 的许可提示

qfluentwidgets 开源协议为 **GPLv3**（商用需购买商业许可）。本项目为个人项目，GPLv3 可接受；若未来有商业化计划，有两个退路：

1. 购买其商业许可；
2. 替换为自研 QSS 主题（PySide6 原生 Widgets + 自定义样式表，工作量约增加 1–2 周）。

**决策：MVP 阶段使用 qfluentwidgets，代码上将 UI 组件封装在 `ui/widgets/` 层，避免业务代码直接依赖组件库，降低未来替换成本。**

## 3. 整体架构

### 3.1 分层架构

```
┌─────────────────────────────────────┐
│  UI 层（ui/）                        │
│  页面 pages / 对话框 dialogs / 组件 widgets │
├─────────────────────────────────────┤
│  服务层（services/）                  │
│  业务用例：创建代办（含重复展开）、归档、延期  │
├─────────────────────────────────────┤
│  领域层（domain/）                    │
│  枚举、纯函数业务规则（重复计算、延期判断）  │
├─────────────────────────────────────┤
│  数据访问层（repositories/）           │
│  查询封装，不暴露 SQLAlchemy 细节给上层   │
├─────────────────────────────────────┤
│  模型层（models/）+ 基础设施（db/）     │
│  ORM 模型、引擎、会话、迁移              │
└─────────────────────────────────────┘
```

**依赖规则**：只允许上层依赖下层；domain 层不依赖任何外层（纯 Python，可 100% 单元测试）。

**层间通信**：服务层操作完成后发射 Qt Signal（如 `task_archived`、`task_changed`），UI 层订阅刷新——列表页、首页、统计页解耦。

### 3.3 开发策略：UI 先行 + Mock 驱动

项目按「界面原型 → UI 实现 → 数据落地」的顺序推进：

1. **界面原型**：先用纯 HTML/CSS 制作静态 demo（`prototype/` 目录，文件结构与实施步骤见 UI 设计文档 §9），作为界面还原的视觉依据，需与 UI 设计文档逐组件走查对齐；
2. **UI 实现**：PySide6 按原型还原界面。**服务层先只定义接口（Protocol）+ 内存 Mock 实现**，UI 只依赖接口编程，此阶段无数据库；
3. **数据落地**：最后实现真实服务（SQLAlchemy/SQLite），通过依赖注入替换 Mock，UI 代码零改动。

约束：

- UI 层 **禁止** import SQLAlchemy / models，只能 import services 接口与 DTO；
- Mock 实现与真实实现共用同一接口（`services/interfaces.py` 定义 `Protocol`），切换由 `app.py` 装配处的开关决定（`USE_MOCK` 配置项）；
- 接口签名在设计时即以真实业务需求为准（含归档、重复展开等），Mock 阶段只做最简内存模拟，复杂规则（重复展开、延期扫描）留给真实实现。

## 4. 数据存储设计

### 4.1 存储位置

- 生产：`%APPDATA%/Shiguang/shiguang.db`（用 `platformdirs` 解析）
- 开发：项目根目录 `./data/shiguang-dev.db`
- 测试：内存 SQLite（`:memory:`），每个测试用例独立

### 4.2 表结构（MVP 部分）

**tasks**（代办与目标统一表，MVP 只用 `kind='todo'`；任务与归档记录合一）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| id | INTEGER PK | 自增 |
| name | VARCHAR(200) NOT NULL | 名称 |
| kind | VARCHAR(10) NOT NULL | `todo` / `goal` |
| period | VARCHAR(10) NOT NULL | `day` / `week` / `month` / `year` |
| repeat | VARCHAR(10) NOT NULL DEFAULT 'none' | 创建时选择的重复规则：`none` / `daily` / `weekly` / `monthly` |
| series_id | VARCHAR(36) NULL | 同一次重复展开生成的记录共享（UUID）；不重复的代办为 NULL |
| date | DATE NOT NULL | 计划日期（每条记录对应一个具体日期） |
| delay_policy | VARCHAR(10) NOT NULL DEFAULT 'default' | `default` / `never` / `auto` |
| delay_count | INTEGER NOT NULL DEFAULT 0 | 自动延期次数（仅记录展示） |
| related_task_ids | JSON | 关联目标 id 列表（v1.0 启用） |
| description | TEXT | 描述 |
| standard | TEXT | 代办流程/完成标准 |
| status | VARCHAR(10) NOT NULL DEFAULT 'pending' | `pending` / `archived` |
| duration | INTEGER NULL | 用时（分钟），归档时写入 |
| score | INTEGER NULL | 质量评分 1–5，归档时写入 |
| summary | TEXT NULL | 总结（可选），归档时写入 |
| archived_at | DATETIME NULL | 归档时间 |
| created_at / updated_at | DATETIME | 时间戳 |

**设计要点**：
- 无模板/实例之分：`repeat != 'none'` 的记录就是创建时展开生成的普通代办记录，`series_id` 标识同批，每条独立展示、独立归档。
- 归档不新建记录：`duration` / `score` / `summary` / `archived_at` 在 `status='pending'` 时为 NULL，归档即 UPDATE 本行。统计模块只查这一张表。
- 索引：`(status, date)`、`(series_id)`。

habits / habit_checkins / diary_entries 三表结构同产品文档 §4，v1.0 前暂不建表，模型与迁移按模块迭代追加。

### 4.3 迁移策略

- Alembic 管理版本；应用启动时自动执行 `upgrade head`，用户无感升级。

## 5. 核心机制设计

### 5.1 启动序列（app.py）

```
启动 QApplication
  → 定位数据目录、初始化 engine
  → alembic upgrade head
  → DelayService.scan()               # 逾期 auto 代办顺延
  → 构建 MainWindow 并显示
  → 启动跨天定时器（QTimer 每分钟检查日期变化，跨天后重跑延期扫描 + 通知 UI 刷新）
```

### 5.2 重复代办展开生成（domain/rules.py 纯函数 + 创建流程调用）

**设计语义**：重复代办在**创建时**一次性展开为多条独立记录——没有模板、没有延迟生成，自然也不需要幂等机制（生成只发生在创建这一刻，一次插入即完成）。

- 纯函数 `expand_dates(repeat, start_date, end_date) -> list[date]`：
  - daily：`[start_date, end_date]` 逐日（含首尾）
  - weekly：从 start_date 起每 +7 天，不超过 end_date
  - monthly：从 start_date 起每月同一日号，不超过 end_date；该月无此日号（如 2 月 31 日）则跳过该月
  - 边界：`end_date < start_date` → 校验失败；首条恒为 start_date（结果不会为空）；结果条数 > 400 → 校验失败，提示缩短日期范围
- `create_todo` 在**同一事务**内批量插入全部展开记录：每条拷贝表单字段，`date` 为各自计划日期，`repeat` 保存创建时的规则，`series_id` 写入同一 UUID
- 展开后记录完全独立：编辑/删除/归档均只作用于单条；删除其中一条不影响同系列其余记录

### 5.3 自动延期（domain/rules.py 纯函数判断）

- 扫描 `status='pending' AND date < today AND kind='todo'` 的代办
- `delay_policy='auto'`：`date = today`，`delay_count += 1`
- `default/never`：保持原日期，UI 以逾期样式展示

### 5.4 归档（services/task_service.py）

归档是同一张表上的**单行 UPDATE**，天然无需跨表事务与幂等设计：

1. 校验任务存在且 `status='pending'`；校验 `score ∈ [1,5]`、`duration > 0`、`summary` 可空（非空限 500 字）
2. UPDATE 本行：`status → 'archived'`，写入 `duration` / `score` / `summary` / `archived_at`
3. 提交后发射 `task_archived(task_id)` 信号

### 5.5 统计查询（MVP）

单表即可支撑全部统计：

- 热力图：`SELECT date(archived_at), COUNT(*) FROM tasks WHERE status='archived' GROUP BY date(archived_at)`
- 完成率：`归档数 / (归档数 + 逾期数 + 今日待办数)`，按周/月聚合，均来自 tasks
- v1.1 评分趋势 / 用时分布：`tasks.score` / `tasks.duration`（`status='archived'`）

## 6. UI 设计规范

> ⚠️ **本节已被《UI 设计文档》（docs/UI设计文档.md）取代。所有界面实现以 UI 设计文档为唯一依据**（设计令牌、页面线框、组件规格、动效、空状态均已完整定义）。以下保留内容仅作快速参考，如有冲突以 UI 设计文档为准。

### 6.1 主窗口

- `FluentWindow`：左侧竖向导航（今日 / 代办 / 日记 / 统计），右侧 `QStackedWidget` 页面容器

- 字体：UI 默认字体回退链 `Segoe UI → Microsoft YaHei UI`

### 6.2 代办页线框

┌──────────────────────────────────────────────┐

│ │ ○ 代办名称          ⭐完成标准  [归档]    │ │  ← TaskCard
│ │   描述摘要…                    周目标·xx  │ │
│ └──────────────────────────────────────────┘ │

| 项 | 值 |

## 10. 风险与备选

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| qfluentwidgets GPLv3 与商业化冲突 | 未来分发受限 | UI 组件封装隔离；备选自研 QSS 主题 |
| PySide6 打包体积大（~100MB+） | 分发包臃肿 | 单目录模式 + 排除无用 Qt 模块；或换 Nuitka |
| 跨天定时器漏触发（休眠等场景） | 自动延期延迟 | 启动时兜底扫描 + 窗口激活事件时补检 |
| SQLite 并发写 | 极低（单机单进程） | WAL 模式 + 单连接串行写 |
